# BYOC Pulsar for Galaxy on SURF Research Cloud

An SRC Ansible component that installs [Pulsar](https://github.com/galaxyproject/pulsar) as a "bring your own compute" (BYOC) endpoint of a Galaxy server that runs the [byoc-sync](https://github.com/sanjaysrikakulam/elixir_biohackathon_2026_project1/tree/main/byoc-sync) pipeline, modelled on [usegalaxy.eu](https://usegalaxy.eu): Pulsar is an AMQP **client** of the Galaxy's RabbitMQ broker (`pulsar_amqp_host`, by default usegalaxy.eu's `mq.galaxyproject.eu`). Supports Ubuntu 22.04 and 24.04.

No broker runs on this workspace. Pulsar connects *to* the Galaxy's RabbitMQ over AMQPS, so this workspace needs no open inbound port; the broker must accept this workspace on its AMQPS port. Files go directly between Pulsar and the Galaxy's HTTPS URL (`/api/`), which the Galaxy's runner sends with every job.

```
Pulsar (this workspace) ──AMQPS──▶ RabbitMQ of the Galaxy, pulsar_amqp_host (user galaxy_<name>_byoc, vhost /pulsar/galaxy_<name>_byoc)
Pulsar ─────── HTTPS for input/output files ───────▶ https://<galaxy>/api/
```

The workspace root (`https://WORKSPACE_HOST/`) is an SRAM-protected **welcome page** with the values to enter in the Galaxy's BYOC form (including the password, each with a copy button) and the state of this Pulsar: whether it is connected to the Galaxy's broker, still waiting for the Galaxy admins to create its account, failing with the check's message, or not checked yet (until the tolerant broker check of issue #22 lands, the page always shows *Not checked yet*).

## byoc-sync is the contract

In the byoc-sync pipeline, the user deploys a Pulsar with a BYOC name and a password, enters them with their compute limits in the `byoc_pulsar` section of their Galaxy preferences (User → Preferences → Manage information), and byoc-sync opens a pull request on the Galaxy's infrastructure repository. Once an admin merges it and the playbook is deployed, Galaxy sends that user's jobs to their Pulsar. Everything on the Galaxy side is derived from the BYOC name (byoc-sync's `naming.py`, usegalaxy.eu's site configuration):

| Object | Value |
| --- | --- |
| RabbitMQ user and vhost | `galaxy_<name>_byoc`, `/pulsar/galaxy_<name>_byoc`, with the form's password |
| Galaxy's job runner (`PulsarMQJobRunner`) | `pyamqp://galaxy_<name>_byoc:<password>@mq.galaxyproject.eu:5671//pulsar/galaxy_<name>_byoc?ssl=1`, `manager: production`, `amqp_acknowledge: true`, `amqp_ack_republish_time: 300`, `amqp_consumer_timeout: 2.0`, `amqp_publish_retry: true` (60 retries) |
| TPV destination | the form's limits; with `nfs_path`: `jobs_directory: <nfs_path>/staging`, `persistence_directory: <nfs_path>/persisted_data`, `SINGULARITY_CACHEDIR: <nfs_path>/var/database/container_cache` |

byoc-sync validates the form (`validate.py`): the name has 3 to 32 characters of `a-z 0-9 _`, starts with a letter, does not end in `_` or `_byoc` and has no `__`; the password has 10 to 128 letters and digits; `nfs_path` is an absolute path of `A-Z a-z 0-9 . _ - /` without `//` or `.`/`..` segments. This component applies the same rules to its parameters, writes Pulsar's `app.yml` to match that runner (the URL without `?ssl=1`, replaced by TLS verification, below; manager `production`; `amqp_ack_republish_time: 300`), uses the storage directory as `nfs_path` (so Galaxy's `jobs_directory` is Pulsar's staging directory) and creates the container cache directory. The tests prove this with byoc-sync's own code and templates (vendored in [`tests/byoc_contract/`](tests/byoc_contract/README.md)).

## SRC catalog setup

1. Create a storage volume in SRC and attach it to this workspace when you create it (SRC mounts it at `/data/<volume name>`). Pulsar keeps all its data there, including its generated credentials.
2. Create an Ansible component using this repository and `playbook.yml` as the script. Install the roles and collections in `requirements.yml` through SRC's Ansible dependency mechanism, as for the [SRC Pulsar component](https://github.com/ErasmusMC-Bioinformatics/src-component-pulsar).
3. Add it to a catalog item using Ubuntu 22.04 or 24.04, **after SRC-Nginx** (for the SRAM-protected welcome page), with these component parameters. The defaults are usegalaxy.eu's:

   | Parameter | Default | Meaning |
   | --- | --- | --- |
   | `pulsar_amqp_host` | `mq.galaxyproject.eu` | the Galaxy's RabbitMQ hostname (the name in its TLS certificate; no `https://` or port) |
   | `pulsar_amqp_port` | `5671` | its AMQPS port |
   | `pulsar_amqp_name` | empty | the BYOC name, the form's `username` (byoc-sync's rule above). Empty: generated, `src` and 8 hex digits, and kept on the storage volume, so a rerun keeps it |
   | `pulsar_amqp_password` | empty | the form's `password` (10 to 128 letters and digits). Empty: generated (24 characters) and kept with the name. Not an SRC secret: the welcome page shows it, for the form |
   | `pulsar_manager` | `production` | the manager byoc-sync's runner uses (fixed in its runner template); change it only for a Galaxy whose runner uses another name, since Galaxy's jobs would otherwise wait in a queue Pulsar never reads |
   | `pulsar_storage_path` | required | the attached volume's mount point `/data/<volume name>` (Pulsar uses its `pulsar` directory) or a directory on it (`A-Z a-z 0-9 _ . -`, at most 255 characters); the form's `nfs_path`, so Galaxy's `jobs_directory` is `<storage directory>/staging`. See [Attached storage](#attached-storage) |
   | `pulsar_apptainer` | `true` | Apptainer for the containers the Galaxy's tools run in |
   | `pulsar_docker` | `false` | Docker Engine, for Docker destinations |
   | `pulsar_cvmfs` | `true` | mounts the Galaxy CVMFS repositories (reference data) |
   | `pulsar_job_runner` | `slurm` | `slurm` runs jobs through Slurm on this workspace (DRMAA), `local` in Pulsar itself |
   | `pulsar_amqp_ack_republish_time` | `300` | the runner's `amqp_ack_republish_time`: seconds before an unacknowledged message is sent again |

   Empty values (how SRC passes an unset parameter) get these defaults; an empty `pulsar_storage_path`, a misspelt `true`/`false` or runner, or a name or password outside byoc-sync's rules is an error. The playbook validates the parameters first and lists every problem without echoing the password. A given name or password replaces the stored one (and is stored in its turn); to get new generated ones, remove `<storage directory>/byoc.json` and rerun.
4. Create the workspace with the storage volume attached. Open `https://WORKSPACE_HOST/` (SRAM sign-in): it shows the broker, user and vhost, and the values for the Galaxy's BYOC form.
5. In the Galaxy (User → Preferences → Manage information → `byoc_pulsar`), enter the page's `username`, `password`, `max_accepted_cores`, `max_accepted_mem` (every vCPU and 90 % of the memory in GB, as the pulsar-byoc playbook suggests; lower them if you like), the GPU limits (0) and `nfs_path` (the storage directory). byoc-sync opens the pull request; after it is merged and deployed, the deployment's broker check (below) passes and Galaxy routes your jobs here. The Galaxy's broker must allow this workspace on `pulsar_amqp_port`.

For a Galaxy other than usegalaxy.eu that runs byoc-sync with the same naming (`galaxy_{x}_byoc`, `/pulsar/galaxy_{x}_byoc`, manager `production`), set `pulsar_amqp_host` (and the port) to its broker. Do not paste the runner's URL into `pulsar_amqp_host`: only the hostname goes there, and the validation never echoes a value with a login.

## What the playbook does

* Installs `pulsar-app[amqp]` 0.15.15 (kombu, py-amqp) and `drmaa` in `/opt/pulsar/venv`, webless with `pulsar-main` in a `pulsar` systemd unit, as in usegalaxy.eu's [NEMO login-node role](https://github.com/usegalaxy-eu/pulsar-nemo-login-role). Jobs run on this workspace through Slurm (below), or with `pulsar_job_runner: local` in Pulsar itself (`queued_python`, vCPUs − 1 concurrent jobs).
* **Loads or generates the BYOC credentials** (`tasks/credentials.yml`, `files/byoc_credentials.py`, run as root with the values on stdin) once the storage is ready: the given `pulsar_amqp_name` and `pulsar_amqp_password`, else the ones in `<storage directory>/byoc.json` from an earlier run, else new ones (`src` and 8 lowercase hex digits; 24 letters and digits, from Python's `secrets`), and keeps what is in effect in that file (`root 0600`, written atomically). A file of another owner, a link, a file readable by others or one with values outside byoc-sync's rules stops the deployment with a message that names the file, never a value. The tasks that handle the password run with `no_log`.
* Writes `/opt/pulsar/config/app.yml` (`root:pulsar 0640`, the only file with the password besides the welcome page and `byoc.json`): `message_queue_url: pyamqp://galaxy_<name>_byoc:<password>@<pulsar_amqp_host>:<port>//pulsar/galaxy_<name>_byoc`, manager `production`, `staging_directory` (`<storage directory>/staging`), `amqp_acknowledge: true`, `amqp_ack_republish_time: <pulsar_amqp_ack_republish_time>` (`300`, as byoc-sync's runner) and the runner's publish retries.
* **Verifies the broker's TLS certificate and hostname**: `amqp_connect_ssl_cert_reqs: cert_required`, `amqp_connect_ssl_ca_certs: /etc/ssl/certs/ca-certificates.crt` (Ubuntu's CA bundle; SRC-Nginx certificates come from Let's Encrypt or ZeroSSL) and `amqp_connect_ssl_server_hostname: <broker host>`.
  * The URL has no `?ssl=1`, unlike the Galaxy README's example: kombu lets the URL's `ssl` replace the `ssl` options Pulsar builds from `amqp_connect_ssl_*`, so with `?ssl=1` nothing beyond the CA chain would be checked. The `amqp_connect_ssl_*` settings switch TLS on by themselves.
  * py-amqp checks the hostname only when `server_hostname` is set, hence the third setting. `cert_reqs` takes the name of the `ssl` constant (`cert_required`); `required` would fail in Pulsar.
  * `tests/test_check_amqp.py` performs real TLS handshakes through Pulsar's connection code: a certificate for another host and one from an unknown CA are both rejected.
* **Checks the connection at deployment** and records the result: `/opt/pulsar/check_amqp.py` connects with `app.yml`'s settings through Pulsar's own code and passively declares Pulsar's setup queue (`pulsar_production__setup`; `pulsar_<manager>__setup` in general, `pulsar__setup` for `_default_`). A consumer on it proves that Pulsar logged in to its vhost and waits for jobs. Galaxy's broker has no management API for Pulsar's user, so this is the check. Its outcome is one of three states, written to `/opt/pulsar/config/byoc-state.json` (`root:pulsar 0640`, `{"state": ..., "message": ..., "checked_at": "<ISO 8601, UTC>"}`), shown on the welcome page and printed by the playbook:
  * `connected`: Pulsar consumes its setup queue as its BYOC user.
  * `waiting`: the broker refused the login or the vhost. byoc-sync creates the RabbitMQ user and vhost only once an admin has merged its pull request and the Galaxy's playbook was deployed, so this is the normal state of a first deployment, and the deployment **passes**. The Pulsar unit keeps trying: Pulsar exits when the broker refuses its login (`files/pulsar_main.py`, which runs `pulsar-main`), and systemd restarts it every 30 seconds without a start limit, so it connects by itself once the account exists. The state file and the welcome page keep saying `waiting` until the component is rerun or the check is run again by hand. A name or password that differs from the form's looks the same: if the state stays `waiting` after the admin merged and deployed, compare them with the form's values (the check's message says so).
  * `error`: anything else, and the deployment **fails** with the check's message: the certificate or hostname is rejected, `pulsar_amqp_port` is not an AMQPS port, the host does not resolve, or, after 24 attempts five seconds apart (about two minutes; up to about six when a firewall drops packets, since each attempt then waits for connection timeouts), the broker is unreachable (firewall) or Pulsar does not consume.

  After the admin merged, rerun the component (it changes nothing but records `connected`), or run the check by hand: `sudo /opt/pulsar/venv/bin/python /opt/pulsar/check_amqp.py /opt/pulsar/config/app.yml` (exit status 0 connected, 3 waiting, 75 not yet, 1 error; one line, never the password). A consumer can also be a half-open connection of an earlier Pulsar with the same name and password, until its heartbeat times out (up to about 20 minutes); give every Pulsar its own name.
* **Checks the attached storage first**, before installing anything, with `files/check_storage.py`, and refuses a `pulsar_storage_path` that cannot safely hold Pulsar's data; see [Attached storage](#attached-storage) for the rules. A volume root that other users can write to gets the sticky bit. The same check runs before every start of Pulsar, Docker and slurmd.
* `force_handlers` restarts Pulsar after a changed `app.yml` or venv even when a later task fails, so a rerun cannot leave the old Pulsar running.
* Publishes the welcome page (`/srv/static/index.html`, readable by nginx only) after the broker check, with its state, and also when Slurm, the installation or the check failed, so the form's values are always available.

### Jobs through Slurm

With `pulsar_job_runner: slurm` (the default), as in the [earlier SRC Pulsar component](https://github.com/ErasmusMC-Bioinformatics/src-component-pulsar/tree/pulsar_attached), Pulsar's manager is `queued_drmaa`: it submits each job through the `slurm-drmaa1` library (`DRMAA_LIBRARY_PATH=/usr/lib/slurm-drmaa/lib/libdrmaa.so.1` in the `pulsar` unit; from the Galaxy project's [slurm-drmaa PPA](https://launchpad.net/~natefoo/+archive/ubuntu/slurm-drmaa), which `galaxyproject.repos` also adds, since Ubuntu has had no slurm-drmaa since 16.04) to a single-node Slurm on this workspace. Galaxy sees no difference: same connection, manager name and queues.

* The signing keys of the slurm-drmaa and Apptainer PPAs ship in this repository (`files/slurm-drmaa.asc`, `files/apptainer.asc`; the tests check their Launchpad fingerprints `8DE68488…12788738` and `F6B0F519…FC6218AE`): a keyserver's export of a key changes between downloads, so downloading it made every rerun report a change. When a PPA rotates its key, replace the file (CI's weekly Slurm live check shows it). An apt preference lets the slurm-drmaa PPA supply only `slurm-drmaa*` packages. The PPA builds amd64 only, so the Slurm runner needs an x86_64 workspace. Another playbook on the same workspace that adds these PPAs without `signed-by` (such as `galaxyproject.repos`) makes apt refuse the conflicting `Signed-By`.
* [galaxyproject.slurm](https://github.com/galaxyproject/ansible-slurm) 1.0.5 with `slurm_roles: [controller, exec]`: this workspace is controller and only node (`localhost`, partition `pulsar`), so no shared filesystem is needed. munge's key is the random one the package generates on this workspace; the playbook neither ships nor reads it, and checks only that it exists and is private to `munge`.
* **Node size from the workspace**: `CPUs` = vCPUs; `RealMemory` = memory minus `pulsar_slurm_reserved_memory_mb` (at least 1 GiB or a tenth, never more than half) for the OS, Pulsar and its broker connection. Slurm drains a node that has less than its configured memory, so the node is never configured larger than the workspace. `select/cons_tres` with `CR_CPU_Memory` lets jobs share the node (Ubuntu 22.04's Slurm would otherwise give each job the whole node), and `DefMemPerCPU` gives a job without a memory request its CPU's share, so every CPU can run a job. Galaxy can still request more per destination (`submit_native_specification`). Memory is not enforced (no cgroup task plugin, `proctrack/pgid`): the numbers only decide how many jobs start, and a job that uses more than its share can still push the workspace into the OOM killer, as with the local runner.
* Jobs run as the `pulsar` user: DRMAA submits as Pulsar's user, and slurmd starts the job as that user. Unlike with the local runner, jobs run outside the `pulsar` unit and so without its sandboxing (`ProtectHome`, `PrivateTmp`, `NoNewPrivileges`): a tool can read world-readable files in `/home` and use the real `/tmp` (only `TMPDIR` points to the storage). Slurm's `TaskProlog` (`/etc/slurm/task_prolog.sh`) gives each job the storage's home, `TMPDIR` and Apptainer directories (Pulsar's own jobs get their home and `TMPDIR` from the unit and keep Apptainer's cache under `~`). Apptainer and Docker work as with the local runner.
* `slurmctld` (6817) and `slurmd` (6818) listen on all interfaces, as Slurm always does; every request is authenticated with this workspace's own munge key. Keep these ports closed to other hosts in the workspace's security group. Slurm's `NoInAddrAny` would bind them to the hostname's address, not to localhost, and break the node's `localhost` address.
* **Docker epilog** (`pulsar_docker: true` only, with `jq`): cancelling a job kills its processes, not the Docker container it started, which runs under dockerd. Slurm's `Epilog` [`files/epilog.sh`](files/epilog.sh), after usegalaxy.org's, runs as root after every job and `docker kill`s the container named in the job's `configs/container_config.json` (Galaxy writes it). That file is the job's, so the epilog reads it with the job user's rights, only as a regular file, with time limits, and kills only a plain container name; it always succeeds, because a failing epilog drains the node. `PrologEpilogTimeout: 90`.
* **On the storage**: job working directories are in staging; slurmd's spool (`SlurmdSpoolDir`) and each job's temporary directory (`TMPDIR`, `<storage directory>/job_tmp/<job id>`, removed by Slurm's `TaskEpilog` when the job script ends; `TmpFS`) are on the storage too, and so is the `pulsar` user's home. Slurm's controller state (`StateSaveLocation`, `/var/lib/slurm/slurmctld`, which keeps each batch script for `MinJobAge`) and logs stay on the root disk. `slurmd`, like Docker, starts only when the storage check passes.
* The deployment waits until the node accepts jobs (`sinfo`) and fails with `scontrol show node localhost` otherwise. `ReturnToService: 2` brings it back by itself after a reboot.
* Slurm accounting is off (no `slurmdbd`), so there is no `sacct`. Inspect jobs with `squeue` (queued and running), `scontrol show job <id>` (also for four hours after the end, `MinJobAge`), `sinfo` (the node) and `scancel <id>`; Pulsar's log has every job. Slurm's logs are in `/var/log/slurm/`.
* Switching to `local` stops and disables `slurmctld` and `slurmd` (Slurm stays installed); switching back starts them again. Pulsar restarts on either switch. Switch when no jobs are active: Pulsar cannot move jobs between managers and reports them to Galaxy as lost.

### Containers and CVMFS

This Pulsar has no Conda, so a tool with requirements only runs in a container. Galaxy resolves the container image and builds the container command line; Pulsar only executes it, so the runtime and every path in that command line must exist here:

* Apptainer (`pulsar_apptainer`, default `true`) from the Apptainer PPA, unprivileged (no setuid starter), with its `singularity` command. usegalaxy.eu's BYOC destinations inherit `pulsar_default`, which runs tools in Apptainer containers; Galaxy's container resolvers give `docker://quay.io/...` images, which Apptainer pulls here on first use (outbound HTTPS needed; the first run of a tool is slow) into `SINGULARITY_CACHEDIR`, `<storage directory>/var/database/container_cache` (byoc-sync's destination, with the form's `nfs_path`).
* Docker Engine (`pulsar_docker`, default `false`) with the `pulsar` user in the `docker` group, which is root-equivalent on the host, for destinations with `docker_enabled`.
* CVMFS (`pulsar_cvmfs`, default `true`): [galaxyproject.cvmfs](https://github.com/galaxyproject/ansible-cvmfs) 0.5.0 (`galaxyproject.org` repositories, 8 GB cache, European stratum 1 first), checked before Pulsar starts. `/cvmfs` is a system-wide Apptainer `bind path`, so tool data table paths (`/cvmfs/data.galaxyproject.org/...`) resolve in jobs, as on usegalaxy.eu.

## Secrets

The password is generated on the workspace (or given as `pulsar_amqp_password`; it is not an SRC secret, since the user must read it from the welcome page to enter it in the form). It is written to `<storage directory>/byoc.json` (`root 0600`), `app.yml` (`0640`, group `pulsar`) and the SRAM-protected welcome page (`root:www-data 0640`). Tasks that handle it use `no_log` and no diff; the validation, the credentials helper and the broker check print no password, and Pulsar masks it in its own log. Anyone with root on this workspace, or on the Galaxy's infrastructure, can read it.

To change it, set `pulsar_amqp_password` (or remove `byoc.json` for a new generated pair) and rerun this component, then enter the new password in the form; byoc-sync updates the vault with it.

The ast-grep rules in `ast-grep/rules/` (tests in `ast-grep/rule-tests/`) refuse `eval`/`exec` and the usual ways of switching off TLS certificate or hostname verification, in Python code and in `amqp_connect_ssl_cert_reqs` of the app.yml template; the pytest tests check the rendered TLS settings themselves. `tests/byoc_contract/` is vendored from byoc-sync and excluded from linting, formatting and coverage.

The tests cover parameter validation against byoc-sync's rules, the names against byoc-sync's `naming.py`, the welcome page's form values through byoc-sync's `validate()`, `app.yml` against the runner byoc-sync's template writes and as Pulsar 0.15.15 reads it (user, vhost, URL, TLS options, queue names), the credentials helper (generation, reuse across runs, given values winning, refused stores, nothing echoed) and its tasks, real TLS handshakes for certificate and hostname verification, the broker check's messages, the state recorded from its exit status and output (`byoc-state.json`), the launcher `files/pulsar_main.py` against a stand-in Pulsar whose consumer thread dies, the playbook's structure, the Slurm settings (rendered with galaxyproject.slurm's own `slurm.conf` template, so install the roles first), the node sizing, the job runner parameter, the epilog against stand-ins for `scontrol`, `jq` and `docker`, and Pulsar building its manager from `app.yml`. `BYOC_SYNC_REPO=/path/to/elixir_biohackathon_2026_project1` also compares the vendored contract files with a byoc-sync checkout; CI does this against that repository's `main` in a separate job, so a change on the byoc-sync side shows up as a failed contract check without hiding this repository's own results.

CI's Slurm live check ([`.github/workflows/slurm-live.yml`](.github/workflows/slurm-live.yml)) runs the playbook on GitHub's Ubuntu 22.04 and 24.04 runners without a Galaxy broker (`--skip-tags broker-check,docker-install`), twice to check that a rerun changes nothing, and then runs jobs as the `pulsar` user through Pulsar's own `queued_drmaa` manager from the deployed venv and `app.yml` ([`tests/live/pulsar_job.py`](tests/live/pulsar_job.py)): one that reports its user and Slurm job, one in Apptainer, one in Docker, and one whose container the epilog must stop. It has no broker: the run from Galaxy is in the molecule test below.

The unit tests stay on 2.18: [`tests/helpers.py`](tests/helpers.py) renders templates with Templar methods that ansible-core 2.19 removed, so the molecule job runs `tests/e2e/galaxy_config.py` with a separate `.venv` of `requirements-dev.txt` (`MOLECULE_TESTS_PYTHON`). ### Integration and end-to-end tests (molecule)

CI's molecule job ([`.github/workflows/molecule.yml`](.github/workflows/molecule.yml), scenario [`molecule/default`](molecule/default)) needs Docker and runs on GitHub's runners only. It starts two SRC test workspaces (`ghcr.io/utrechtuniversity/src-test-workspace`) on one Docker network, privileged and with systemd; it uses Docker (rootful and privileged) for the privileges Slurm and the volume need:

* `galaxy` (Ubuntu 24.04), alias `galaxy.molecule.test`: a Galaxy's RabbitMQ as BYOC Pulsars see it (Ubuntu's package, AMQPS only with a certificate for `galaxy.molecule.test` from a test CA, node `rabbit@localhost`, no `guest`), with what byoc-sync's pull request creates: user `galaxy_molecule_byoc` and vhost `/pulsar/galaxy_molecule_byoc` with the form's password;
* `pulsar` (Ubuntu 24.04, and 22.04 in a second job): this playbook with `pulsar_amqp_host: galaxy.molecule.test`, the given name `molecule` and password, `pulsar_job_runner: slurm` and `pulsar_storage_path: /data/molecule/pulsar` on a separate ext4 volume of the runner. The test CA goes into the system CA bundle, as a public CA is there on SRC, so Pulsar's certificate and hostname verification stay on.

The playbook runs twice (the second run must change nothing). The verify step then checks that `check_amqp.py` passes and the recorded state is `connected`, that Pulsar's `app.yml` verifies the certificate and hostname (and that the same settings with a wrong hostname are refused), that the credentials are stored root-only in `byoc.json` and are the given ones, that the container cache is the `pulsar` user's inside root-owned parents, that Pulsar, munge, slurmctld and slurmd are active and the Slurm node takes jobs, that Pulsar's data directories (staging, persisted data, home, job temporary files, slurmd's spool, Apptainer's directories, the container cache) are on the storage mount, and, on the broker, that a consumer of `pulsar_production__setup` on `/pulsar/galaxy_molecule_byoc` exists and `galaxy_molecule_byoc` is connected over TLS. It then plays the BYOC pipeline: with the account removed from the broker (as before byoc-sync's pull request is merged) the playbook passes and records `waiting` while the unit keeps restarting Pulsar; with the account created again Pulsar connects by itself, and a rerun records `connected`. Last, a run against a broker host that does not resolve must fail and record `error`.

The end-to-end test then submits a job the way Galaxy does. [`tests/e2e/galaxy_config.py`](tests/e2e/galaxy_config.py) derives the form and the names from the component parameters and renders Galaxy's `PulsarMQJobRunner` runner and TPV destination for them from byoc-sync's own `runner.yml.j2` and `destination.yml.j2` (vendored, checked against byoc-sync's `main` by the contract job); Galaxy's client connects as the BYOC user with the runner's URL. On the Galaxy workspace, [`tests/e2e/galaxy_job.py`](tests/e2e/galaxy_job.py) does with Pulsar's client library as Galaxy 26.1 pins it (`pulsar-galaxy-lib`, [`tests/e2e/requirements-galaxy.txt`](tests/e2e/requirements-galaxy.txt)) what Galaxy's runner does: it builds the client manager from the runner's parameters, consumes status updates and acknowledgements, lays out the job with the destination's parameters (`remote_transfer`, `rewrite_parameters`), submits a small job (sort a file, report user, Slurm job and working directory) and waits for its final status. A small HTTP server stands in for Galaxy's job files API at `galaxy_url`: Pulsar fetches the input from it and posts the outputs back. The test passes when the job completed with exit code 0 after a `running` status update, both outputs arrived, and the job ran as `pulsar` in a Slurm job in `/data/molecule/pulsar/staging/<job>/`. The unit tests run the same client against an in-process Pulsar on kombu's in-memory transport. The test does not exercise Galaxy's tool, dependency or container handling, so the destination's `singularity_enabled`, `remote_metadata` and `outputs_to_working_directory` play no part in it.

To run it elsewhere, install `requirements-dev.txt`, `molecule/requirements.txt`, `requirements.yml` and `molecule/default/requirements.yml`, mount an ext4 volume at `/mnt/molecule-volume` (or `MOLECULE_STORAGE`; prepare refuses anything else), and run `molecule test` with Docker. `MOLECULE_DISTRO=ubuntu_jammy` tests Ubuntu 22.04. For SRC's Ansible, install `molecule/requirements.txt` with `ansible==14.6.0` instead, `requirements-dev.txt` into a separate virtualenv, and set `MOLECULE_TESTS_PYTHON` to its `python`.

## Attached storage

All of Pulsar's data lives on the workspace's attached storage volume, never on the root disk. `pulsar_storage_path` is required. Set to the volume's mount point, `/data/<volume name>`, it stands for the directory `/data/<volume name>/pulsar`, which the deployment creates; any deeper path is used as it is. With `/data/pulsar_storage` (or `/data/pulsar_storage/pulsar`), the layout is:

| Path | Owner | Contents |
| --- | --- | --- |
| `/data/pulsar_storage/pulsar` | `root:root 0755` | the storage directory: the form's `nfs_path` |
| `…/byoc.json` | `root 0600` | the BYOC name and password in effect (given or generated), reused by every rerun |
| `…/staging` | `pulsar 0750` | job inputs, outputs and working directories: Pulsar's `staging_directory`, Galaxy's `jobs_directory` |
| `…/home` | `pulsar 0750` | `HOME` of Pulsar and its jobs (the unit's and the task prolog's `HOME`; `/etc/passwd` keeps `/var/lib/pulsar/home`, as `usermod` cannot change the home of a user with running processes) and Pulsar's working directory: what jobs keep under `~`, such as Pulsar's tool `dependencies` and, for Pulsar's own jobs, Apptainer's cache (they keep only `HOME`, `PATH` and `TMPDIR` of the unit's environment) |
| `…/persisted_data` | `pulsar 0750` | job state and message acknowledgement stores |
| `…/apptainer_cache` | `pulsar 0750` | Apptainer's image cache (`APPTAINER_CACHEDIR`) for Slurm jobs, with `pulsar_apptainer`; Pulsar's own jobs (local runner) drop that variable and use `~/.apptainer/cache` in the home |
| `…/apptainer_tmp` | `pulsar 0750` | Apptainer's build space (`APPTAINER_TMPDIR`) for Slurm jobs, with `pulsar_apptainer`; Pulsar's own jobs build in `TMPDIR` |
| `…/job_tmp` | `pulsar 0750` | jobs' temporary files (`TMPDIR`): shared by Pulsar's own jobs (from the `pulsar` unit; tools usually clean up, check it now and then), a directory per Slurm job (from Slurm's task prolog, removed after the job); also Slurm's `TmpFS` |
| `…/var/database/container_cache` | `pulsar 0750` (in root's `var/database`) | Galaxy's `SINGULARITY_CACHEDIR` for this Pulsar's jobs, where byoc-sync's destination points it |
| `…/slurmd` | `root 0755` | slurmd's spool (`SlurmdSpoolDir`: job scripts and running jobs' state), with `pulsar_job_runner: slurm` |
| `…/docker` | root (created by dockerd) | Docker's `data-root` (images, containers), with `pulsar_docker`; the containerd image store, Docker 29's default, is switched off so that images are here and not in `/var/lib/containerd` |

The venv (`/opt/pulsar/venv`) and the configuration (`/opt/pulsar/config`, with the password) stay on the root disk: they are small and rebuilt by every deployment. The credentials travel with the volume on purpose, so a new workspace on the same volume keeps its Galaxy account. The storage directory belongs to root, and the playbook does not follow links when it creates directories, so jobs running as `pulsar` cannot make a later deployment hand other directories to `pulsar`.

The check refuses a path on the root file system (also SRC's mount point directory while the volume is not attached), on tmpfs or a similar file system, with a symbolic link in it, that is a volume's mount point itself, or where root cannot create a file and give it to another user (read-only, NFS `root_squash`, FUSE without `allow_other`); with `pulsar_docker`, also one on a network or FUSE file system, where Docker's overlay2 does not work. The storage directory must not be replaceable by other users: below the volume's mount point every existing directory up to the storage directory must be root's, and none may be writable by group or others without the sticky bit. The deployment sets the sticky bit on a volume root that others can write to (they can then still create and use their own files there, but not rename or delete Pulsar's directory).

The `pulsar` unit, and Docker's and slurmd's through drop-ins, run the check (`/usr/local/libexec/pulsar-src/check_storage.py`, as root) before every start: if the volume is missing at boot, however SRC mounts it, they do not start rather than write to the empty mount point on the root disk, and retry (every 30 seconds for Pulsar, 10 for Docker and slurmd) until the volume is there. They deliberately have no `RequiresMountsFor`: a failed or late mount would fail their start as a dependency, which systemd does not retry; `After=local-fs.target remote-fs.target` only stops them before the volume is unmounted at shutdown. Docker's `daemon.json` is written before Docker is installed, so its first start already uses the storage; a Docker installed earlier is restarted onto it (its running containers stop). A drop-in left from an earlier deployment is removed when Docker or the Slurm runner is switched off.

**Reusing a volume.** Rerunning the component, or a new workspace with the same volume and `pulsar_storage_path`, reuses the data on it. If the `pulsar` user's uid or gid differs from the one that wrote it (a new workspace), the playbook stops Pulsar and hands the old owner's files in the `pulsar`-owned directories (`home`, `staging`, `persisted_data`, `job_tmp`, `apptainer_cache` and `apptainer_tmp` above) to the new `pulsar` user, owner and group only; files of other users, and root's, are left alone. Pulsar is started again afterwards, also when a later task fails. The data is kept and reused, with the same BYOC name and password (`byoc.json`), so Galaxy needs no change; whether Pulsar can finish jobs from an earlier workspace depends on that Galaxy still waiting for them. Deleting the workspace keeps the volume.

**Changing the path.** Let running jobs finish first (`squeue` empty: slurmd's spool moves with the path, and Slurm loses jobs that are still running). Set `pulsar_storage_path` to the new directory and rerun this component; it creates a fresh layout there and leaves the old directory as it is (move the data first with Pulsar stopped if you want to keep it, `byoc.json` included: without it, the rerun generates new credentials, unless you pass the old ones as parameters). The form's `nfs_path` changes with it: enter the new one in the Galaxy's `byoc_pulsar` form, and byoc-sync updates the destination. With Docker, images in the old `data-root` (and in `/var/lib/docker` from a Docker installed before this component) are not moved; Docker pulls them again.

**Upgrading from a version with `pulsar_staging_dir`.** That version kept staging in `pulsar_staging_dir` (default `/mnt/pulsar/files/staging`), persistence in `/var/lib/pulsar/persisted_data`, and the home with Apptainer's cache (`.apptainer`) and Pulsar's tool `dependencies` in `/var/lib/pulsar/home`. Let running jobs finish, set `pulsar_storage_path`, update the form as above and rerun; then remove `/var/lib/pulsar`, the old staging directory and Docker's `/var/lib/docker` to free the root disk (the playbook no longer uses them). To keep job state, cached images or dependencies, stop Pulsar and move `persisted_data`, the staging directory's content, `.apptainer` and `dependencies` into the new layout before the rerun.
